# Хендофф: переписывание серверной части АКГ на модульную архитектуру

**Для:** Валентин Демихов (0xVLTN)
**Задача:** переписать серверную часть сервиса маркетинг-отчётности АКГ «Капитал» —
сделать её модульной: отдельный модуль-коллектор на каждый канал, все они пишут
нормализованные данные в **SQL-базу**; отдельный модуль-экспортёр выгружает из базы
куда нужно (Google-таблица / PDF / прочее).

**Дата:** 28.07.2026 · составлено по итогам аудита текущей системы.

---

## 1. Что делает сервис (бизнес-суть)

Клиент — **АКГ «Капитал» / Osnova Capital** (направление ГК Диалектика). Продукт —
**еженедельная маркетинговая отчётность**: собрать статистику из всех маркетинговых
каналов, свести в единый реестр по неделям, показать в рабочей Google-таблице клиента
и раз в неделю прислать собственнику PDF-отчёт (план/факт по каналам).

Единица данных — строка **(неделя × канал)** с метриками: охват, визиты, клики,
подписчики (прирост), лиды, сделки, оплаты, расходы, комментарий.

## 2. Каналы и как из них берутся данные

Каналы делятся на две группы по способу доступа — это **ключевое ограничение**
для новой архитектуры (не всё собирается с сервера).

### 2.1. API-каналы (собираются с сервера, есть программный доступ)
| Канал | Источник | Нюансы |
|---|---|---|
| Яндекс.Метрика | `api-metrika.yandex.net` | визиты/посещения; OAuth-токен ~1 год |
| Яндекс.Директ | `api.direct.yandex.com/json/v5/reports` | расходы/клики; OAuth |
| Битрикс24 | REST-webhook `ag-capital.bitrix24.ru/rest/...` | лиды/сделки/оплаты |
| VK Ads (реклама) | `ads.vk.com/api/v2` | рекламные метрики; refresh-токен |
| Telegram | Bot/Metrics | охват/подписчики |

⚠️ **Битрикс — самое важное бизнес-правило:** ~97% «маркетинговой» выручки в Битриксе
на деле делает клиентский сервис. Поэтому лиды/сделки фильтруются **по ID менеджеров
маркетинга** (лист «Справочник_менеджеров»). Оплата считается по статусу **WON и полю
`MOVED_TIME`** (не `CLOSEDATE`). Классификация канала: `Канал*` → `Источник*` → `UTM` →
`SOURCE_ID`; неизвестный `utm_source` → «Прочие источники, новые utm-метки».

### 2.2. Агентские каналы (нет пригодного API — собираются Playwright-агентом на ПК Анны)
Эти три канала **нельзя** взять с сервера: нет публичного API нужной статистики,
Дзен-Студия/ВК-дашборд требуют живой залогиненной сессии, а VPN (Amnezia) на ПК
оператора обходится только Яндекс.Браузером. Поэтому их собирает клиентский
Playwright-агент (репозиторий `akg-agent-mode`, каталог `channels/`):

| Канал | Способ | Нюансы |
|---|---|---|
| **Дзен · 2 кабинета** (Корп `osnova_capital` + ЛБ `ekimovskih`) | XLSX-экспорт из Студии | эндпоинт `publisher-publications-rich-stat-xls?filterType=by-event&from=&to=` (события ЗА ПЕРИОД, НЕ lifetime — прежний вариант завышал в десятки раз). Охват = показы. 2 разных Яндекс-аккаунта → **перелогин** между заходами (`--dzen-account 1|2`) |
| **ВК · 1 аккаунт, 2 сообщества** (Корп `agcapital` + «ВК ЛБ» `irina.ekimovskih`) | скриншот дашборда → распознавание Claude vision | оба сообщества за 1 заход (перелогин НЕ нужен). Вкладки: Сообщество/Посты/Видео/Канал. Подписчики = **прирост за период (может быть отрицательным)**. ⚠️ НЕ ставить `page.route`-фильтров — рвут SPA-дашборд |
| **Тенчат ЛБ** | XHR `account/stats` (JSON) | период фиксирован платформой «последние 7 дней» |

Разбор и рабочие тонкости каждого канала — в `channels/*.py` и `docs/recon/` этого репозитория.
Агент нормализует метрики в строки реестра (`core/registry_rows.py`) и шлёт их на сервер.

## 3. Текущая архитектура (as-is) — что переписываем

**Топология:**
- **Сервер 5.187.1.162** — прод `akg-native` (Docker, Node.js), `/opt/akg-native/`.
  Домен `n8n.crm-techno.ru` указывает на него, эндпоинты `/native/webhook/*`. Сервер клиента.
- **Сервер 178.104.156.39** — сервер Маши (`mariiastar`), `~/AKG/owner-report-pipeline/` —
  генерация PDF (Python + weasyprint) и SMTP-отправка. Плюс dev-копия натива.
- **Google** — таблица клиента «План-факт отдела маркетинга Капитала_2026», лист
  «Реестр_факта», Apps Script (`Code.gs`, ~778 строк) под аккаунтом `summonerx222`.

**Как течёт (важно — это модель «посчитать на лету», без хранения):**
1. **Нет ни одного крона сбора.** API-каналы считаются **on-demand** в одной большой
   ноде `Pull_+_map_to_detailed_channels.js` (~93 КБ) при каждом вызове
   `GET /webhook/akg-report-rows` — живые HTTP-запросы к Метрике/Директу/Битриксу/VK Ads.
2. Агент шлёт строки vk/дзен/тенчат в `POST /webhook/agent-metrics` → кладутся в
   `staticData.agent_rows[week]` (нода `Agent_Metrics_Code.js`).
3. `Pull + map` при сборке **замещает** свои слабые Дзен/ВК/Тенчат данными агента
   (Битрикс-лиды/VK Ads в этих каналах сохраняются).
4. Запись в Google-таблицу — триггер Apps Script `pullWeekly` **ежедневно ~06:00 МСК**:
   `GET akg-report-rows` → пишет в «Реестр_факта» (дедуп неделя+канал, бережёт «Комментарий»).
5. Снэпшот таблицы в xlsx — триггер `pushXlsxDaily` **04:00 МСК** → `/webhook/akg-xlsx-upload`.
6. **Отчёт** (по команде Анны): агент `--report` → `POST /webhook/generate-report` (5.187)
   → по **ssh 5.187→178** → `gen_and_send.sh` → `inject_week.py` (целевая неделя живьём
   из `akg-report-rows`, при сбое — фолбэк на xlsx-снэпшот) → `make_report.py` (PDF det+mini,
   `--upload` в storage `/webhook/akg-owner-report`) → `send_report.py` (SMTP).

**Проблемы этой модели (почему и переписываем):**
- Монолитная нода `Pull + map` — вся логика всех каналов в одном файле; тяжело тестировать/менять.
- Нет хранения истории — всё пересчитывается на лету при каждом запросе (медленно, хрупко).
- Данные агента попадают в **таблицу** с лагом до суток (только на следующем `pullWeekly`);
  на отчёт не влияет (он читает сервер напрямую), но человеко-видимая таблица отстаёт.
- Двухсерверная связка через ssh (5.187→178) ради генерации PDF — лишняя точка отказа.
- Секреты/токены живут в `staticData` и хардкодом в ноде.

## 4. Целевая архитектура (as-desired) — что нужно построить

**Идея (от Alex):** модульность + единый источник правды в SQL.

```
[коллектор: Метрика]  ─┐
[коллектор: Директ]   ─┤
[коллектор: Битрикс]  ─┤──→ нормализованные записи ──→  [ SQL-база ]  ──→ [экспортёр: Google-таблица]
[коллектор: VK Ads]   ─┤        (неделя × канал)                          [экспортёр: PDF-отчёт]
[коллектор: Telegram] ─┘                                                  [экспортёр: прочее/API]
[ingest: агент vk/дзен/тенчат] ─┘ (пуш с ПК Анны)
```

**Принципы:**
1. **Один модуль = один канал.** У каждого коллектора единый интерфейс (напр.
   `collect(week) -> list[FactRow]`), своя изоляция кредов, свои тесты. Логика Метрики
   не знает о логике Битрикса.
2. **SQL — единственный источник правды.** Таблица фактов с ключом (неделя, канал) +
   история. Идемпотентный upsert (повторный сбор перезаписывает строку недели+канала,
   как сейчас дедуп). Плюс справочники (каналы, менеджеры, план).
3. **Экспортёры отделены от сбора.** Модуль выгрузки читает из SQL и рендерит: в
   Google-таблицу (замена `pullWeekly`), в PDF (замена `make_report`), потенциально в
   любой другой приёмник. Экспортёр не собирает — только читает БД.
4. **Расписание сбора — явное.** Планировщик (cron/systemd-timer/очередь) запускает
   коллекторы (напр. ночь Вс→Пн для API-каналов), они пишут в БД. Это закрывает
   расхождение из аудита: сейчас «ночного сбора» нет, всё on-demand.
5. **Агентские каналы — через ingest-эндпоинт в ту же БД.** Playwright-агент на ПК Анны
   остаётся (для vk/дзен/тенчат иначе никак), но пушит строки в **ingest-модуль**, который
   пишет в SQL напрямую (замена `agent-metrics`+`staticData`). После пуша данные сразу в БД →
   экспортёр в таблицу их видит немедленно (лаг шага 3 исчезает).
6. **PDF — на том же сервере.** Убрать ssh-связку 5.187→178: генерацию PDF (weasyprint/шаблоны
   с 178) перенести на основной сервер как экспортёр-модуль, читающий из SQL.

**Открытые решения (обсудить Alex ↔ Валентин):**
- СУБД: PostgreSQL (рекомендация — надёжно, есть история/аналитика) vs SQLite (проще).
- Где живёт БД и сервис: остаёмся на 5.187 или новый инстанс.
- Язык: сейчас натив на Node.js; коллекторы можно на Python (агент уже Python) — на выбор.
- Судьба сервера 178 после переноса PDF (оставить только как бэкап Маши).

## 6. Модель данных (черновик схемы фактов)

Из полей текущего реестра (колонка в скобках — как в «Реестр_факта»):
`week_start` (Дата/Ключ недели), `channel` (Канал детальный, F), `category`/`group`/`responsible`
(из справочника каналов), `expenses` (Расходы), `reach` (Охват, K), `visits` (Визиты, L),
`clicks` (Клики), `subs_social` (подписчики соцсети — **прирост**, M), `subs_email`, `subs_bot`,
`leads`, `qleads` (качественные), `deals` (созданные), `won_deals` (успешные), `participants`,
`revenue` (Сумма продаж), `comment` (Комментарий, W — **бережём при перезаписи**).
Ключ upsert — (week_start, channel). Отдельно: справочники каналов/менеджеров, план на месяц.
